# CaseDock

客服工单与知识服务。

需要Go 1.22 或更新版本。

查看命令帮助：

```sh
go run . --help
```

启动本地服务：

```sh
go run . serve --host 127.0.0.1 --port 8080 --data-dir data
```

打开 http://127.0.0.1:8080 查看首页并登记工单。Ctrl+C 停止服务。`--data-dir` 指定本地业务数据目录，重启时继续使用同一目录，工单记录与成功的提交标识都会保留。

首页可填写问题描述、联系人、联系方式、来源（在线/电话/邮件）、类别、优先级（低/普通/高/紧急），以及可选的附件说明和关联订单号（只保存文字）。提交成功后显示新工单编号并出现在列表中，可查看每条工单的完整登记内容。

接口：

- `GET /health` 返回服务状态和产品名称。
- `GET /api/tickets` 返回工单列表，结构为 `{"tickets":[...]}`，按创建时间从新到旧排列，首次启动时为空。
- `POST /api/tickets` 接收 JSON 登记一张工单，成功（201）返回新工单；内容相同的重复提交（200）返回原工单。
- `POST /api/tickets/{id}/assignment` 接收 JSON 分派或转交工单负责人，成功（200）返回 `{"ticket":{...},"changed":...}`，即当前工单及本次是否改变了负责人。

`POST /api/tickets` 的 JSON 字段：

| 字段 | 说明 |
| --- | --- |
| `description` | 问题描述，必填，保留正文换行 |
| `contactName` | 联系人，必填 |
| `contactInfo` | 联系方式，必填，字符串保留前导零 |
| `source` | 来源，必填，只能是 `在线`/`电话`/`邮件` |
| `category` | 类别，必填，由用户填写 |
| `priority` | 优先级，必填，只能是 `低`/`普通`/`高`/`紧急` |
| `attachmentNote` | 附件说明，选填，只保存文字，保留正文换行 |
| `orderNumber` | 关联订单号，选填，字符串保留前导零 |
| `submitId` | 非空的提交标识，由调用方为本次填写生成 |

文字字段会去除首尾空白后校验；同一 `submitId` 提交相同内容返回原工单（不新增记录、编号与时间不变），提交不同内容返回 409 且不改动记录；尚未成功的提交可修正内容后沿用原标识。错误码：缺少必填、选项非法或 JSON 无法解析返回 400，提交标识冲突返回 409，读取或保存失败返回 500，错误信息区分具体原因。

`POST /api/tickets/{id}/assignment` 的 JSON 字段：

| 字段 | 说明 |
| --- | --- |
| `assignee` | 负责人，必填，按文字保存，去除首尾空白后必须有内容，且不能是 `未分派` |
| `operationId` | 非空的操作标识，由调用方为本次分派生成，在同一工单内识别重复提交 |

首次分派与随后的转交都使用这个接口。负责人实际变化时，工单会追加一条分派记录（原负责人、新负责人、发生时间，首次分派的原负责人为 `未分派`），并刷新最近处理时间；负责人与当前相同视为成功（`changed` 为 `false`），不追加记录、不刷新时间。同一 `operationId` 提交相同负责人为幂等重放，返回当前工单且不做任何修改（即使工单后来已转交给别人，也不会被改回）；同一标识提交不同负责人返回 409 且不改动任何内容；校验失败或保存失败的标识可在修正后重试。错误码：负责人不合要求、操作标识缺失或 JSON 无法解析返回 400，工单不存在返回 404，操作标识冲突返回 409，保存失败返回 500。分派结果、分派记录与成功的操作标识随工单数据一起保存，重启后继续有效；登记的 `submitId` 与分派的 `operationId` 互不影响。

在首页打开工单详情即可填写负责人并提交分派，详情中按发生顺序展示完整分派记录，尚未分派时显示暂无分派记录。

```sh
curl http://127.0.0.1:8080/health
curl http://127.0.0.1:8080/api/tickets
curl -X POST http://127.0.0.1:8080/api/tickets \
  -H 'Content-Type: application/json' \
  -d '{"description":"无法登录","contactName":"张三","contactInfo":"010-88886666","source":"电话","category":"账号","priority":"高","submitId":"sub-0001"}'
```

未知路径返回 404，已知路径不支持的方法返回 405，`Allow` 响应头列出该路径实际支持的方法（`/api/tickets` 为 `GET, POST`，`/api/tickets/{id}/assignment` 为 `POST`，其余路径为 `GET`）。

## 分派功能的端到端回归测试

`e2e/` 目录是工单详情页分派功能的浏览器端到端回归测试，使用 Node 内置测试运行器与 `puppeteer-core`（复用系统已安装的 Chrome/Chromium，不额外下载浏览器）。每个用例都会构建当前源码、在随机端口启动真实服务（独立临时数据目录），并经一个本地代理访问页面：普通接口原样转发，分派接口可被挂起后再放行，从而确定性地覆盖“提交后等待结果期间继续填写负责人”的场景。

运行环境：Node.js 22+、可用的 Chrome/Chromium（默认取 `/usr/bin/google-chrome`，可用环境变量 `CHROME_BIN` 指定其他路径）。

```sh
cd e2e
npm install
npm test
```

覆盖内容包括：

- 等待期间把负责人改成另一个名字：旧请求成功后，列表与详情显示服务确认的负责人、最近处理时间与分派记录；输入框原样保留返回时的内容（含首尾空白）；成功提示区分“实际分派给谁”与“输入框内容尚未提交”；按钮恢复但不会自动二次分派，由用户决定是否再次提交。
- 等待期间主动清空、或仅增删名字两端空白都算编辑：成功后不填回已提交负责人；清空时提示当前为空且未提交，恢复后仍须填写有效负责人才能再次分派。等待期间完全没有改动时，沿用成功后清空输入的现有行为。
- 提交的负责人与当前负责人相同：仍成功但不新增分派记录、不刷新最近处理时间，草稿保留规则一致。
- 保存失败响应与无法连接服务：不提示成功，提示区分失败的是此前提交的负责人、当前输入只是未提交内容；输入按当前内容保留、按钮恢复，列表与详情不被失败结果改写，重试只由用户主动发起。
- 列表重新读取后同步已打开的详情：详情仍停留在正在查看的同一张工单，负责人、最近处理时间与分派记录与该工单在列表中的同一份内容一致；同步不清除负责人草稿（含首尾空白）、不覆盖现有提示、不在分派等待期间恢复按钮；详情已关闭时不会被重新打开。
